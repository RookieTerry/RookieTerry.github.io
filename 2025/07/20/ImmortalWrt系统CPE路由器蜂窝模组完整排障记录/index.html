ImmortalWrt系统CPE路由器蜂窝模组完整排障记录

本文最后更新于：5 小时前

前情提要

由于我租住的房子没有接入光纤网络，无法办理宽带，我便只能研究起流量卡的上网方案。在互联网上的中文技术论坛浏览了相关的讨论帖，发现大家都极为推崇CPE路由器，优点是插入流量卡上网很稳定。但是一般的大品牌国产CPE路由器功能又太过单一，例如没有收短信的功能，而我的流量卡有时会用来接收一些短信验证码。

爱好折腾网络设备的我又怎能甘心，就开始在国内二手平台上“寻宝”，没想到还真让我发现了一款不一般的CPE路由器：它是一款出口澳洲电信Telstra的出口版CPE路由器，并且还预装了类似于OpenWrt的ImmortalWrt系统，可玩性显著高于一般的国产CPE路由器。这款路由器搭载了Qualcomm IPQ8072A的芯片，Cortex-A53架构，并且蜂窝网络采用的是Quectel（移远）的5G模组。看价格挺合适，于是果断拿下，没想到插上流量卡并使用了一段时间以后，却发现了一些小问题。下面就跟随我的笔记一起，来复盘一下完整的排障记录。

遇到的问题和排错过程

QModem插件自动覆盖网络接口配置

在插入流量卡并完成路由器配置后的最初几天，5G 模组能够正常连接，QModem 的“拨号总览”页面显示绿色的“已连接”状态。

最初在“移动网络 → 拨号总览”中启用 QModem 自动拨号后，QModem 会创建名为 wwan0 的逻辑接口，并运行DHCP协议。该接口能够提供 IPv4 网络，但当时无法稳定获得 IPv6 地址及向 LAN 下发 IPv6 前缀。取消“启用拨号”后，手工创建 proto='quectel' 的 wwan0 接口，则能够获得运营商下发的 IPv6 地址。

问题在于，这个手工接口不能稳定保留。路由器重启、QModem 重拨或执行 /etc/init.d/qmodem_network restart 后，可能出现以下情况：

  • network.wwan0 被重新创建或删除；
  • proto、device、ifname、DNS 等字段被 QModem 改写；
  • LuCI 中的接口消失或显示“错误：网络设备不存在”；
  • QModem 的模组状态变为红色“未连接”；
  • 即使已经执行 uci commit network，下一次重拨后配置仍会发生变化。

这说明问题不是 UCI 没有提交成功，而是提交以后仍有其他进程继续修改 /etc/config/network。OpenWrt 的 UCI 只负责保存配置；如果后台服务之后再次执行 uci set、uci delete 和 uci commit，原有配置仍会被覆盖。UCI 和 netifd 的职责可分别参考 OpenWrt 官方的 UCI 与 netifd 项目。

自定义网络配置持久化

执行 uci commit 只能保存当前内容，不能阻止 QModem 后续再次执行 uci set 或 uci delete。要真正持久化配置，必须让 QModem 保留拨号与状态检测能力，同时停止它对已有用户接口的自动覆盖和删除。

之前使用的uci set qmodem.4_1.define_connect='0'命令来“禁用自动创建/删除 UCI 网络接口”，但define_connect 只在部分 AT 拨号分支中决定使用哪个 PDP context，并没有控制 set_if() 或 flush_if() 是否运行，因此不能依靠这个选项解决接口覆盖问题。

我还尝试过使用 iface hotplug 在 wwan0 ifdown 时重新写回 UCI。该方法存在几个问题：

  • QModem 删除 section 时不一定产生可供该脚本捕获的 ifdown 事件；
  • hotplug 中再次执行 network reload 可能触发新的接口事件，形成递归或事件风暴；
  • 每次恢复都重复 add_list dns，可能生成重复 DNS 项；
  • 它只是在接口被删除后补写，不能阻止 QModem 先破坏正在运行的 netifd 状态。

手动重启网络才出现IPv6接口

这些接口，执行/etc/init.d/network restart后才生成wwan0_4和wwan0_6这两个逻辑接口，并获得 IPv6 地址和 LAN 前缀。

network restart 的作用不是单纯刷新 LuCI，而是停止并重新启动 netifd 管理的协议流程，重新读取 /etc/config/network，再次运行 proto='quectel' 的协议处理器。wwan0_4 和 wwan0_6 是该协议流程在运行时注册的动态逻辑接口；如果第一次协议初始化发生在模组控制口或 QMAP 网卡就绪之前，它们就不会生成。

手工执行 network restart 时，模组通常已经完成 USB 枚举、网络注册和 QMAP 数据接口创建，所以第二次协议初始化能够成功生成动态接口。

我曾经尝试以下做法：

  • 在 qmodem_network start_service() 中立即执行 network reload；
  • 在 wwan0 ifup hotplug 中执行 network reload；
  • 在 wwan0_1 add/ifup 后执行 ifup wwan0_4、ifup wwan0_6；
  • 统一增加 sleep 5、sleep 20 或 sleep 30。

这些方法在实际调试过程中均未稳定解决问题。主要原因是：

  1. network reload 可能发生得太早，且不一定重置失败的协议实例；
  2. 在 iface hotplug 中再次 reload network 容易形成重复事件；
  3. wwan0_4、wwan0_6 尚未被 netifd 注册时，执行 ifup 没有可操作对象；
  4. 固定延时无法适应 USB 枚举、SIM 解锁和运营商注册时间的波动。

因此，应保留“完整 network restart 能恢复”的已验证结论，但把自动化方式改为“等待实际设备就绪后，只在每次开机执行一次”。可以创建 /etc/init.d/restart-network：

长期运行后IPv6地址消失

最开始，我认为长期 IPv6 丢失是因为QMI 模式下 DHCPv6/PD 客户端不会像 IPv4 一样自动续租，但这种说法存在问题。OpenWrt 的 odhcp6c 本身负责 DHCPv6、前缀委派和租约生命周期；如果租约无法续期，应继续检查客户端进程、上游会话、netifd 动态接口及 QMI data call，而不能直接认定“不支持续租”。

当前设备上的实际现象是：运行一段时间后，wwan0_6 可能从 netifd 中消失，IPv6 默认路由或公网连通性随之丢失；此时执行完整的 network restart 可以重新创建动态接口并恢复 IPv6。因此更准确的描述是：

QMI/IPv6 会话或 netifd 动态协议状态在长期运行后没有自动恢复，导致 wwan0_6、IPv6 地址、默认路由或前缀委派中的一个或多个状态失效。

我编写的原有检测脚本存在以下问题：

  • 任意一次 ping 失败就立即重启整个网络，容易因移动网络瞬时抖动造成重启风暴；
  • ping 未指定出口接口，可能使用其他 IPv6 路由；
  • 同时要求 wwan0_4 正常，会把纯 IPv4 逻辑状态误算为 IPv6 故障；
  • 没有锁，cron 上一次尚未结束时可能再次启动；
  • 每十分钟持续写详细日志文件，可能造成不必要的日志增长；
  • 只检查 br-lan 地址，不能区分上游 IPv6、默认路由和 LAN 前缀哪个环节失效。
